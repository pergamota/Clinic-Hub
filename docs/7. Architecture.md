# Architecture

## Overview

ClinicHub follows a classic **layered architecture**, separating concerns
into distinct responsibilities. Each layer only talks to the layer directly
below it — a Controller never talks to a Repository directly, for example.

```
┌─────────────────────────────────────────────────────────┐
│                        Client                           │
│         (Postman, Swagger UI, Frontend / fetch())       │
└───────────────────────────┬─────────────────────────────┘
                            │ HTTP (JSON)
                            ▼
┌─────────────────────────────────────────────────────────┐
│                       Controller                        │
│   @RestController — routing, @Valid trigger, HTTP status│
│   never contains business logic                         │
└───────────────────────────┬─────────────────────────────┘
                            │ DTO
                            ▼
┌─────────────────────────────────────────────────────────┐
│                        Service                          │
│   @Service — business rules, orchestration              │
│   uses Mapper to convert DTO <-> Entity                 │
└───────────────────────────┬─────────────────────────────┘
                            │ Entity
                            ▼
┌─────────────────────────────────────────────────────────┐
│                       Repository                        │
│   extends JpaRepository — persistence only              │
└───────────────────────────┬─────────────────────────────┘
                            │ SQL (via Hibernate)
                            ▼
┌─────────────────────────────────────────────────────────┐
│                         MySQL                           │
└─────────────────────────────────────────────────────────┘
```

## Why DTOs instead of exposing entities directly

Entities (`@Entity`) represent how data is stored in the database. DTOs
represent how data travels through the API. They are kept separate for
three reasons:

1. **Sensitive data leakage** — `User` has a `password` field (hashed, but
   still). It should never be serialized into an API response.
2. **Decoupling the public contract from the database schema** — renaming a
   column or changing a relationship shouldn't break API clients.
3. **Lazy-loading serialization issues** — entities use
   `FetchType.LAZY` on relationships; serializing them directly outside of
   an active Hibernate session can throw `LazyInitializationException`.

Each entity typically has a `RequestDTO` (input, no `id`, no
system-generated fields) and a `ResponseDTO` (output, includes `id`).
Some entities also have a dedicated update DTO when only a subset of
fields should be editable (e.g. `AppointmentStatusUpdateDTO`,
`ExamResultUpdateDTO`) — enforcing at the type level that certain fields
(like who a doctor's linked user is, or an appointment's patient/doctor)
are immutable after creation.

## Mapper layer

`Mapper` classes are stateless, static-method utility classes — never
Spring beans — with a single responsibility: convert between DTOs and
entities in both directions (`toEntity`, `toResponseDTO`). Mappers never
query the database; resolving a foreign key (e.g. turning a `specialtyId`
into a real `Specialty` object) is always done in the Service layer, which
has access to the relevant repositories.

## Authentication & Authorization

Authentication is **stateless**, based on JWT:

```
1. POST /api/auth/login (email + password)
2. Server validates credentials (BCrypt), issues a signed JWT
3. Client stores the token and sends it on every subsequent request:
   Authorization: Bearer <token>
4. JwtAuthenticationFilter intercepts every request, validates the
   token's signature and expiration, and populates the Spring Security
   context — no database lookup or session state required per request
```

Authorization is enforced at two levels:

- **Route-level**, in `SecurityConfig`: which paths require authentication
  at all (`/api/auth/**` and static frontend/Swagger assets are public;
  everything else requires a valid token).
- **Method-level**, via `@PreAuthorize("hasRole('ADMIN')")` (and
  combinations like `hasRole('DOCTOR') or hasRole('ADMIN')`) on individual
  controller methods, restricting specific operations to specific roles.

## Exception handling

A single `@RestControllerAdvice` (`GlobalExceptionHandler`) centralizes
error handling for the entire API, translating custom exceptions into
consistent HTTP responses instead of leaking stack traces:

| Exception | HTTP Status | When |
|---|---|---|
| `ResourceNotFoundException` | 404 | An entity lookup by id fails |
| `InvalidCredentialsException` | 401 | Login fails (wrong email/password) |
| `BusinessRuleException` | 409 | A business rule is violated (duplicate CRM/CPF/email, past-dated appointment, etc.) |
| `MethodArgumentNotValidException` | 400 | Bean Validation fails (`@NotBlank`, `@Email`, etc.) |
| `DataIntegrityViolationException` | 409 | Database-level constraint violation (uniqueness or foreign key), distinguished by inspecting the root cause message |
| `Exception` (fallback) | 500 | Any unforeseen error — returns a generic message, never leaks internal details |

## Testing strategy

Unit tests isolate the Service layer from the database using Mockito:
`@Mock` replaces each Repository dependency, `@InjectMocks` builds a real
Service instance with the mocks injected via constructor — mirroring
exactly how Spring's dependency injection works in production, without
requiring a real database connection. Each test maps to one branch
(decision point) of the method under test: one test per exception path,
plus one for the success path.

## Containerization

The application is packaged with a **multi-stage Docker build**:

1. **Build stage** (`maven:3.9-eclipse-temurin-21`) — compiles the project
   and produces the executable `.jar`.
2. **Runtime stage** (`eclipse-temurin:21-jre`) — a minimal image containing
   only the JRE and the compiled `.jar`, without build tools.

`docker-compose.yml` orchestrates the application together with a MySQL
container on a shared network. Within that network, the application
reaches the database by service name (`db`), not `localhost` — the
datasource URL uses `${DB_HOST:localhost}`, defaulting to `localhost` for
local development outside containers, and set to `db` via the Compose
environment for containerized runs. A MySQL healthcheck combined with
`depends_on: condition: service_healthy` ensures the application only
starts after the database is ready to accept connections.

## Frontend

The frontend is vanilla HTML/CSS/JavaScript (ES Modules), served as static
resources directly by Spring Boot from `src/main/resources/static/`. It
follows a simple component pattern: functions that render `innerHTML`
(`renderHeader()`, `renderFooter()`), a single reusable modal
(`openModal(type)`), and a `services/` layer — one file per entity —
wrapping `fetch()` calls with a shared `apiRequest()` helper that attaches
the JWT `Authorization` header and normalizes error handling across all
three dashboards (Admin, Doctor, Patient).
